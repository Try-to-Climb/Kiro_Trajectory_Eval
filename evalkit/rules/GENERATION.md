# Two ways to generate rules

Rules can be hand-written, or generated by an LLM. There are currently two
generation routes; both produce **intent-form** `.checks.json`
(same shape as `agent-eval.intent.checks.json`), and both are evaluated by
the same engine.

| | One-shot | Stepwise |
|---|---|---|
| Script | `rules/generate-rule.sh` | `rules/genrule/` |
| LLM calls | 1 | 10–16 turns (ACP single session) |
| Wall time | ~3 min | ~2.5 min (three agents in parallel is the same order of magnitude) |
| Input | Full `AUTHORING.md` + agent config | agent config + prompt + skill descriptions + subagent list |
| Intermediate output | None | `*.policy_ir.json`, human-reviewable |
| Multi-purpose agent | One file | One file per task type |

## Usage

One-shot generation:

```bash
cd evalkit
# edit the AGENT_JSON path at the top of rules/generate-rule.sh, then
bash rules/generate-rule.sh
```

Stepwise generation:

```bash
cd evalkit

# (1) Preview just the task-type partition (1 turn, ~6s); confirm the split
#     looks sensible before continuing
python3 rules/genrule/extract_tasks.py <agent.json | prompt.md>

# (2) Full extraction (task types -> per-phase policies -> backbone);
#     one IR file per task type
python3 rules/genrule/generate.py <agent.json | prompt.md>

# (3) Compile to a rule file (pure code, no LLM)
python3 rules/genrule/compile_ir.py rules/genrule/out/<name>.policy_ir.json \
    --out rules/genrule/out/<name>.checks.json

# (4) Self-check + evaluate (reuses the existing engine)
python3 -m rule.runner rules/genrule/out/<name>.checks.json --compile
python3 -m rule.runner rules/genrule/out/<name>.checks.json --session <sid>
```

Output lands in `rules/genrule/out/`; hand-written rules under `rules/` are
not overwritten. Details in [`genrule/README.md`](genrule/README.md).

## Measured results (on agent-eval)

Same agent under test, three rule files compared:

| | Hand-written | One-shot | Stepwise |
|---|---|---|---|
| Rules | 14 | 27 | 29 |
| required | 5 | 11 | 6 |
| Phases covered | Phase 1–4 | Phase 1–5 | **Phase 1–8, full** |
| pipeline quality | good (last step is dispatch) | good (last step is dispatch) | poor (all four steps are `write`) |
| Generalising to broad entries (`dispatches eval-*`) | yes | yes | no |
| `if_claims` fakery detection | no | 3 rules | no |
| Dispatch broken down to specific sub-agents | no | yes | yes |

**Stepwise wins on breadth, not accuracy.** It extracts phase by phase so the
latter half of the prompt (reporting, self-reflection, live-run validation,
in-depth evaluation) does not get missed; but expressive completeness lags
one-shot — the `pipeline` does not pick out the key moments, same-kind
rules are not collapsed into a broader one, and `if_claims` is not used.

The cause is structural: one-shot reads the full `AUTHORING.md`, so it can
copy §4's `pipeline` example and §2's full intent table verbatim; the
stepwise route's three prompts are a **paraphrase** of `AUTHORING.md`, and
the paraphrase lost those parts. The fix is to attach the relevant
`AUTHORING.md` sections verbatim during the policy / backbone turns, rather
than rewriting them.

## How to choose

- **Need a usable rule file fast** → one-shot. Most complete expression, one call.
- **Agent under test has a long flow with many phases and you worry the
  back half will be missed** → stepwise.
- **Agent under test has multiple mutually exclusive purposes** → stepwise.
  It splits by task type, avoiding "the rule written for task A judging a
  run of task B" (measured: of 22 agent-eval sessions only 5 followed the
  orchestration flow, the rest had entirely different task types).
- **Need highest precision** → hand-write, or use a generated file as a
  starting draft and close the loop by hand. Generated outputs currently
  need a human pass for two things: over-broad targets (e.g.
  `reads *.json`, `runs mkdir*`), and precise prohibitions the DSL cannot
  express (distinguishing `python3 x.py` execution from `cat x.py`
  inspection requires a low-level `type` + `exclude` multi-tool regex).

## About severity

Both routes can only infer the level from prompt wording, whereas `required`
really means "must happen on every legitimate run" — a fact the prompt does
not carry. The stepwise route adds seven `required`-demotion rules in-prompt
(marked optional, requires user confirmation, conditional, only applies in
part of the scope, auxiliary artefact, depends on existing state, uncertain),
which brought agent-eval's `required` count from 29 down to 6.

If you have several **known-legitimate** real runs of the **same task
type**, hit-rate calibration can be used:

```bash
python3 rules/genrule/compile_ir.py <ir.json> --calibrate <sid1> <sid2> ... --out <checks.json>
```

Hit rate 1.0 with sample size ≥5 → required; partial hit → recommended;
zero hit → optional with REVIEW; a prohibition violated by a legitimate run
is dropped and reported. Leave-one-out cross-validation shows ordering
rules (`pipeline` / `before`) are the least stable, so they are capped at
recommended across the board.
