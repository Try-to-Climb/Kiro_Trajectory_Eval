evalkit — Supported Features

Same starting point: an agent run's trace (hook / official Kiro session) → normalized into a unified action sequence → four complementary paths. The first three deliver verdicts; the last one delivers comprehension. Click a card for more detail.
Trajectory Eval Did the agent follow the expected behavior/pipeline? Were required steps taken, in the right order, with no forbidden actions, and did claims match reality?
Core8 checkers: Milestone · Forbidden · Exists · Count · Before · IfThen · Produces · LLMJudge
AuthoringOne .checks.json per agent, written in a structured intent DSL (reads/runs/dispatches/pipeline/never_*/if_claims…)
ExtrasLLM-based rule generation (genrule) + pre-compile self-check + configurable scoring (scoring.json)
CatchesRequired steps / ordering / counts / forbidden zones / claim-vs-action consistency / artifact verification
PASS / WEAK / FAIL Health score 0–1 Per-check ✓/✗ + reason rule/ + rules/
Questions it answers
  • Required steps: key steps must appear (collect → probe → dispatch)
  • Ordering: a must precede b; the full skeleton must run in order
  • Counts: action occurrences must fall within a sane range (≥N / ≤N)
  • Forbidden zones: privilege escalation / dangerous commands / scope overflow → immediate FAIL
  • Claim consistency: if the agent claims it did X, there must be action evidence of X
  • Artifact verification: key outputs must be written to disk (auto-matched to write actions)
  • Reasoning quality (optional): LLMJudge scores selected dimensions
Supporting tools
  • genrule/: LLM reads AUTHORING.md + agent config and auto-generates rules
  • pipeline.py: auto-picks the rule file by agent name and runs eval end-to-end
  • --compile: pre-compiles rules; invalid rules are rejected before eval
  • scoring.json: weights / FAIL conditions / all-or-nothing scoring

Completion Eval Did the agent actually do what the user asked? Break the user's ask into atomic requirements, hunt for evidence per requirement, draw conclusions with citations
FlowNine-step forensic pipeline: requirements → claims → criteria → search → re-probe → filesystem crosscheck → judge
LLM useLLM is called at only 4 points; everything else is deterministic. Every LLM output passes a validation gateway; invalid action IDs are rejected as hallucinations.
SafeguardBuilt-in control group: a fabricated requirement is injected; if the system judges it satisfied, the whole run is tagged INVALID
Evidence levelsdirect · artifact · cross_session · derived · retrieved · none
PASS / WEAK / FAIL / INVALID Completion % Overclaim list goal/
Questions it answers
  • Does requirement R1.x have direct evidence?
  • Did an artifact land on disk within the time window?
  • Is this only inferable indirectly, or do we have hard evidence?
  • Did the agent claim something it never actually did → overclaim
  • Can the final answer be verified? If not → unverifiable rather than false
Nine-step workflow
  • s1 map / s2 extract requirements / s2b inject control group / s3 extract claims
  • s4 compile criteria / s5 search / s6 re-probe / s7 filesystem crosscheck / s8 judge / s9 aggregate
  • Verdict power lives only in s8; earlier steps emit candidates only. LLM failures degrade to "recall gaps" rather than wrong verdicts.
  • Human-confirmed requirements can be injected via --requirements
Known limits
  • s2 extraction varies across runs → use --requirements for important evals
  • Responses not collected by default → outcome-type requirements go unverifiable (fix via --with-responses)
  • Official source timestamps are second-precision

Efficiency Eval Was this run worth what it cost? Not about correctness — about time, compute, and redundancy
SegmentAuto-segments the run into task segments anchored by prompts (s2)
LedgerPer segment: duration · credits · cycles · LLM reqs · ctx% (s3)
DuplicationMinHash + embedding multi-dim voting finds duplicate action pairs (s4) + embedding cache
GradingGrades each segment by credits/turn (s8)
Segment ledger Duplicate pairs Efficiency grade efficiency/
Questions it answers
  • How many credits / turns / seconds did each task segment cost?
  • Are there duplicate actions (reading the same file 5 times, re-skinned commands, resent requests)?
  • Which segment has an abnormally high credits/turn?
  • Is context usage approaching the window limit?
  • Is the LLM request count out of control?
Similarity voting (s4)
  • Command-strong: fingerprint of the shell command after stripping noise
  • Path similarity: Jaccard overlap of touched paths
  • Semantic similarity: embedding + MinHash
  • If any dimension passes threshold → marked as duplicate with a reason
Infrastructure
  • embed_cache.py: cross-run embedding cache
  • evidence/canonicalize.py: shell command unwrapping + structure_hash to denoise before comparison

Questions it answers
  • What did each turn do, and what did it produce?
  • How does data flow between turns?
  • Which action generated this artifact, and who used it afterward?
  • When debugging a FAIL verdict, which step didn't register?
  • How do I view the timing in Jaeger / Tempo?
Core capabilities
  • Activity / Entity / Edge model with CERTAIN / LIKELY / WEAK confidence
  • Edge kinds: used_by / generated_by / connected_by / informed_by
  • Per-turn folding: keep only entities shared across turns, drop local noise
  • Shell AST: parses cat / cp / > / tee / python I/O for read/write intent
  • Per-turn thinking: the agent's own reasoning is surfaced on each turn card
Export targets
  • Single-page HTML (open in a browser)
  • DOT / JSON (feed Graphviz or custom pipelines)
  • OTLP/JSON (feed Jaeger / Tempo / otel-collector)
